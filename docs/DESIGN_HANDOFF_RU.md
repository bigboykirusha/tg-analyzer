# TG Analyzer - дизайн-документ для передачи дизайнеру

## 1. Что это за продукт

`TG Analyzer` — это не мессенджер и не CRM. Это узкий аналитический продукт для разбора одного Telegram-чата за раз.

Основной пользовательский сценарий:

1. Пользователь логинится через Telegram.
2. Выбирает конкретный чат.
3. Запускает парсинг.
4. Получает компактный, насыщенный, визуально понятный отчет по этому чату.

Важно: продукт не про “бесконечную ленту данных”, а про сфокусированный аналитический срез.  
Его ценность — превратить историю общения в понятную картину:

- кто больше ведет разговор;
- когда чат оживает;
- как выглядит темп общения;
- какие слова, эмодзи и типы сообщений доминируют;
- где есть длинные паузы и как меняется динамика.

## 2. Продуктовая рамка для дизайна

Это ключевые ограничения, которые дизайнеру нельзя размывать:

- Продукт должен ощущаться как **privacy-first analytics tool**, а не как социальная сеть.
- Основной объект интерфейса — **чат и его аналитика**, не пользовательский профиль.
- Визуальный стиль должен быть **сдержанным, уверенным, плотным по информации**, без маркетинговой “сахарности”.
- Интерфейс должен помогать **сканировать, сравнивать и интерпретировать**, а не просто “любоваться графиками”.
- Главный эмоциональный эффект:  
  **спокойный контроль + интеллектуальная ясность**.

Если коротко: это не “яркий consumer app”, а “умный персональный аналитический инструмент”.

## 3. Аудитория

Основные сегменты:

- люди, которым интересно смотреть на динамику личной переписки;
- пользователи, которые любят метрики, паттерны, quantified-self;
- создатели контента / аналитически настроенные пользователи, которым важна визуальная интерпретация;
- пользователи, чувствительные к приватности.

Что это значит для дизайна:

- нельзя уходить в сухой back-office;
- но и нельзя делать интерфейс слишком “игровым” или декоративным;
- UI должен быть эстетичным, но зрелым;
- каждая секция должна ощущаться как полезный аналитический блок.

## 4. Общий визуальный тон

### Текущая визуальная база

Сейчас проект использует темную тему как основную.

Базовые токены из кода:

- фон страницы: почти черный `#0a0a0a`
- surface: `#111111`
- elevated surface: `#1a1a1a`
- акцент: кислотно-лаймовый `#e8ff6b`
- основной текст: `#f0f0f0`
- вторичный текст: `#888888`
- tertiary text: `#555555`
- success: `#4ade80`
- warning: `#fbbf24`
- danger: `#f87171`
- info: `#60a5fa`

Шрифты:

- основной: `DM Sans`
- моно: `DM Mono`

### Как это должно ощущаться

- тихо;
- технологично;
- собранно;
- дорого без пафоса;
- визуально чисто;
- акцентно, но не кислотно в каждой точке.

### Что важно сохранить

- темную базу;
- светлый текст с высокой читабельностью;
- один яркий акцентный цвет как навигационный и action-сигнал;
- моно-типографику для чисел, длительностей, метрик, процентов.

### Что дизайнер может менять

- уточнить оттенки dark palette;
- нормализовать контраст между слоями;
- пересобрать поверхность карточек;
- аккуратно улучшить глубину, тени, translucency;
- сделать более цельную иерархию заголовков и подписей.

### Что дизайнеру не стоит делать

- делать светлую тему как primary без отдельного продуктового решения;
- превращать интерфейс в dashboard-CRM с холодной enterprise-эстетикой;
- использовать слишком много разноцветных акцентов;
- перегружать фон декоративными эффектами.

## 5. Текущая дизайн-система в коде

### Радиусы

Сейчас используются небольшие радиусы:

- `5px`
- `8px`
- `10px`
- `12px`

Это правильное направление.  
Для продукта лучше держать интерфейс **слегка острым**, а не “слишком мягким”.

### Отступы

Сетка уже построена на кратных шагах:

- 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64

Это хорошая база.  
Дизайнеру стоит использовать её как основу spacing rhythm.

### Базовые компоненты

Уже есть:

- `Button`
- `Badge`
- `MetricCard`
- `SegmentedControl`
- `PopoverMenu`
- `ConfirmDialog`
- `EmptyState`
- `Skeleton`
- `StatusDot`
- `ParseProgress`

То есть проект уже не с нуля.  
Задача дизайнера — не выдумывать все заново, а собрать из этого цельную систему.

## 6. Информационная архитектура продукта

Сейчас у продукта три основных экрана:

1. `Login`
2. `Dashboard`
3. `Chat Report`

Это и есть основной дизайн-контур.

### 6.1 Login

Роль экрана:

- объяснить продукт;
- дать ощущение доверия и приватности;
- провести пользователя через auth flow: phone -> code -> password.

Что уже есть:

- трехколоночный layout на desktop;
- центральная auth panel;
- боковые информационные блоки;
- language switch;
- trust-блок;
- легкий hero-like визуальный фон.

Что дизайнер должен решить:

- сделать login визуально более цельным и премиальным;
- выровнять copy-блоки и auth-card в одну систему;
- не допустить ощущения “лендинга отдельно от продукта”.

Принцип:

- login должен быть красивым,
- но по тону оставаться частью аналитического продукта,
- а не маркетинговым сайтом.

### 6.2 Dashboard

Роль экрана:

- это operational hub;
- здесь пользователь выбирает чат;
- здесь видит историю запусков;
- здесь управляет парсингом;
- здесь понимает, что уже проанализировано.

Основые блоки dashboard:

- список доступных для парсинга чатов;
- состояние активного парсинга;
- история запусков;
- список готовых отчетов;
- служебные действия: logout / terminate telegram / delete account / clear history.

Что по UX критично:

- пользователь должен быстро понять, какой чат уже проанализирован;
- какой чат сейчас парсится;
- где можно запустить новый парсинг;
- что делать, если сессия Telegram неактивна;
- чем отличается “уже есть отчет” от “недавно перепарсили”;
- что скрыто из-за лимита списка чатов.

Dashboard по характеру должен быть:

- плотным;
- сканируемым;
- очень ясным по статусам;
- без декоративного шума.

### 6.3 Chat Report

Это главный продуктовый экран.

Роль:

- превратить сухие метрики в понятную историю общения.

Текущая структура:

- overview
- rhythm
- words
- timeline

Внутри отчета уже есть:

- KPI-блоки;
- relationship dynamics;
- message composition;
- activity heatmap;
- weekday pattern;
- hourly chart;
- daily volume;
- popular words;
- emoji split;
- distinctive / unique vocabulary;
- silence periods;
- sessions;
- insights;
- export/share surface.

Это не просто отчет со статистикой.  
Это экран, который должен давать ощущение:

“я понял характер этого чата”.

## 7. Принципы интерфейса, которые нужно сохранить

### 7.1 High information density without chaos

Информации много, но она должна быть:

- разбита на логические секции;
- визуально иерархична;
- пригодна для быстрого обзора;
- пригодна для вдумчивого чтения.

### 7.2 Numbers are first-class citizens

Метрики здесь — не второстепенный декор.  
Числа, проценты, длительности, доли и счетчики — это ядро интерфейса.

Нужно:

- выделять их типографически;
- использовать моноширинный стиль там, где это помогает;
- не прятать важные числа в мелкий текст.

### 7.3 Status clarity

Парсинг — асинхронный процесс.  
Поэтому статусы должны быть очень понятны:

- pending
- running
- completed
- failed
- cancelled
- inactive / busy / cooldown

Нельзя делать статусы двусмысленными.  
Для каждого статуса нужны:

- цвет;
- текст;
- понятное место в layout;
- при необходимости действие рядом.

### 7.4 One-screen comprehension

На каждом основном экране пользователь должен быстро понять:

- где он находится;
- что здесь главное;
- что можно сделать дальше.

## 8. Экран Login: рекомендации дизайнеру

### Цель

Сделать auth flow визуально уверенным, безопасным и нестрессовым.

### Что важно в композиции

- центральная auth-card — главный фокус;
- боковые блоки — вторичный контекст, а не шум;
- progress индикатор шагов должен быть максимально понятным;
- language switch должен выглядеть нативно и спокойно.

### Желаемый эффект

- продукт выглядит серьезным;
- вход понятный;
- пользователь не боится передавать Telegram-авторизацию.

### Что можно улучшить

- сделать левую и правую колонки более содержательно согласованными;
- выровнять напряжение между hero-copy и auth-flow;
- улучшить визуальное различие между “информацией” и “формой ввода”;
- сделать privacy/secure messaging более убедительным и системным.

## 9. Экран Dashboard: рекомендации дизайнеру

### Главный вопрос пользователя на экране

“Что я могу проанализировать прямо сейчас и что уже готово?”

### Иерархия блоков

Рекомендуемый приоритет:

1. активный parse state;
2. список доступных чатов;
3. готовые отчеты;
4. история запусков;
5. служебные действия.

### Что должно хорошо работать визуально

- активный parse должен быть заметен сразу;
- готовые отчеты должны отличаться от “доступных чатов без отчета”;
- history не должна перетягивать внимание у основного действия;
- пустые/заблокированные/загружающиеся состояния должны быть штатной частью дизайна.

### Важные сценарии состояния

Нужно явно продумать дизайн для:

- загрузки списка чатов;
- ошибки загрузки чатов;
- Telegram session busy;
- session inactive;
- active parse;
- cooldown после недавнего парсинга;
- truncated dialog list;
- пустой history;
- отсутствия готовых отчетов.

### Ошибка, которую нельзя допустить

Dashboard не должен превращаться в “таблицу всего подряд”.  
Это должен быть управляемый аналитический хаб, а не склад сущностей.

## 10. Экран Chat Report: рекомендации дизайнеру

### Роль экрана

Это главная витрина продукта.  
Если дизайнер будет вкладываться только в один экран, то это должен быть именно report.

### Что должно быть сильным

- структура секций;
- ритм между графиками и фактами;
- иерархия заголовков;
- визуальная подача relationship dynamics;
- подача insight-блоков;
- общее ощущение “аналитического story view”, а не просто набора карт.

### Важные принципы

- каждая секция должна отвечать на конкретный вопрос;
- длинные страницы должны читаться блоками;
- графики не должны быть декоративными, они должны быть интерпретируемыми;
- тексты-подсказки должны объяснять смысл, а не повторять заголовок.

### Ожидаемая структура восприятия

Пользователь идет так:

1. быстро считывает общую картину;
2. понимает баланс и ритм;
3. смотрит, чем наполнено общение;
4. замечает необычные паттерны;
5. получает “инсайты” как сжатую интерпретацию.

### Где дизайнер особенно нужен

- relationship section;
- insight cards;
- composition section;
- переключение между `overview / rhythm / words / timeline`;
- mobile-поведение длинного аналитического отчета.

## 11. Навигация

### Desktop

Сейчас используется боковой sidebar:

- логотип;
- пользователь;
- language switch;
- dashboard;
- report;
- logout.

Это правильно для desktop.

### Mobile

Сейчас navigation схлопывается в компактный top bar.

Это тоже правильное направление, но дизайнеру нужно:

- проверить удобство tap targets;
- сделать mobile nav ещё более очевидной;
- убедиться, что report screen не теряет контекст на мобильном.

### Что важно

Навигация должна быть минимальной.  
Продукт узкий, поэтому не нужно раздувать IA.

## 12. Компонентные правила

### Кнопки

Есть 4 базовых роли:

- primary
- secondary
- ghost
- danger

Для дизайнера это значит:

- primary — только для действительно главного действия;
- secondary — рабочие действия;
- ghost — мягкие действия / вспомогательная навигация;
- danger — destructive actions.

### Badge / StatusDot

Используются для:

- статуса job;
- вторичного состояния сущности;
- коротких semantic signals.

Нужно следить, чтобы статусные цвета были едины во всем продукте.

### Metric cards

Это базовая единица аналитического представления.  
Метрика должна содержать:

- label;
- крупное значение;
- короткое пояснение.

Дизайнеру важно не переукрасить metric cards.  
Они должны быть читаемыми, а не “глянцевыми”.

### ParseProgress

Это очень важный компонент.  
Он должен быть:

- заметным;
- живым;
- понятным;
- не тревожным;
- с ясным прогрессом и ясной возможностью отмены.

## 13. Графики и аналитические блоки

Уже есть следующие типы визуализаций:

- heatmap;
- balance chart;
- composition chart;
- daily volume chart;
- hourly chart;
- weekday chart;
- emoji / word blocks.

### Что дизайнеру нужно определить

- единый визуальный язык графиков;
- правила подписей осей;
- правила подзаголовков и подсказок;
- когда график должен быть compact, а когда section-width;
- как выглядят empty states внутри графиков;
- как выглядят hover / tooltip / active states.

### Принцип

Графики должны быть:

- визуально родственными;
- не слишком яркими;
- легко сравнимыми между собой;
- не требовать “дешифровки”.

## 14. Контент и микро-копирайтинг

### Общий тон текста

Тон продукта:

- спокойный;
- умный;
- не мемный;
- не корпоративно-сухой;
- без псевдопсихологии.

### Тексты должны

- объяснять, а не украшать;
- называть вещи прямо;
- помогать интерпретировать данные;
- не драматизировать инсайты.

### Чего избегать

- слишком “человеческих” выводов о чувствах;
- кликбейтных формулировок;
- назидательного тона;
- лишней романтизации.

## 15. Mobile-first замечания

Хотя продукт аналитический, mobile должен быть полноценным.

Особенно важно:

- KPI не должны ломаться по ширине;
- сегменты и табы должны оставаться usable;
- графики должны иметь нормальную высоту;
- длинный report должен сохранять ритм;
- sticky/mobile progress не должен перекрывать контент;
- destructive actions не должны теряться.

### Что проверить в макетах

- длина русских текстов;
- длинные названия чатов;
- много цифр в метриках;
- empty states;
- loading blocks;
- toast / floating feedback.

## 16. Состояния, которые дизайнер обязан отрисовать

Минимальный обязательный список:

### Auth

- ввод телефона;
- ввод кода;
- ввод пароля 2FA;
- loading;
- ошибка;
- success transition.

### Dashboard

- загрузка чатов;
- пустой список;
- truncated list warning;
- session inactive;
- telegram busy;
- active parse;
- cancel in progress;
- empty history;
- history with failures;
- ready reports.

### Report

- loading report;
- report unavailable / error;
- reparse running;
- no text data;
- no emoji / no words;
- no insights;
- no long silences;
- export in progress.

## 17. Что уже хорошо и не требует переизобретения

- темная база продукта;
- акцентный лаймовый сигнал;
- компактные радиусы;
- сочетание `DM Sans` + `DM Mono`;
- sidebar + content layout на desktop;
- плотная аналитическая структура report page;
- pattern “metric cards + larger section cards”.

Это можно улучшать, но не нужно ломать концептуально.

## 18. Что дизайнер может пересобрать смелее

- login composition;
- dashboard information hierarchy;
- report section rhythm;
- surface hierarchy;
- badges/status visuals;
- chart presentation language;
- mobile analytics reading flow;
- empty/loading/error states.

## 19. Что дизайнеру важно знать о данных и логике

- Один пользователь может иметь только один активный parse одновременно.
- Отчеты строятся по одному чату.
- Есть cooldown после недавнего парсинга.
- Есть история запусков.
- Есть live progress через websocket.
- Не все диалоги всегда доступны в списке, потому что есть лимит листинга.
- Продукт хранит агрегаты, а не должен выглядеть как просмотрщик сообщений.

Это важно, потому что дизайн не должен обещать сценарии, которых нет в логике.

## 20. Рекомендации по финальному deliverable от дизайнера

Ожидаемый результат от дизайнера:

1. Полный desktop-flow:
   - login
   - dashboard
   - active parse on dashboard
   - report
   - report loading / empty / error

2. Полный mobile-flow:
   - login
   - dashboard
   - report
   - sticky / compact progress

3. Базовая design system:
   - colors
   - typography
   - spacing
   - cards
   - buttons
   - badges
   - input fields
   - tabs / segmented controls
   - status visuals
   - chart style guidance

4. State library:
   - loading
   - empty
   - error
   - success
   - destructive confirm
   - disabled

5. Короткие правила handoff для разработки:
   - размеры
   - отступы
   - behavior notes
   - responsive notes
   - priorities

## 21. Короткий итог для дизайнера

Нужно спроектировать не “красивый Telegram-сервис”, а **сфокусированный темный аналитический инструмент**, который:

- выглядит уверенно;
- уважает приватность;
- хорошо работает с плотной информацией;
- объясняет паттерны общения;
- не превращается в шумный дашборд;
- держит в центре один качественный отчет по одному чату.

Если понадобится, следующим шагом можно подготовить еще и **экран-by-экран дизайн-бриф в формате задач для Figma**: отдельно для `Login`, `Dashboard`, `Report`, `Components`, `States`, `Mobile`.
