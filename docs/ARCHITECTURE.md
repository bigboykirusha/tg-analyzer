# Архитектура

```text
Браузер ──HTTPS──> Nuxt (web) ──/api proxy──> Fastify API ──> PostgreSQL
   │                                              │
   └──────────── WSS (одноразовый ticket) ────────┤──> Redis ──> BullMQ worker ──> Telegram
```

## Поток анализа

1. Пользователь входит по номеру телефона (код, при необходимости пароль 2FA). Строка Telegram-сессии шифруется AES-256-GCM и хранится в `telegram_sessions`.
2. Дашборд показывает диалоги (`GET /parse/dialogs`, кэш в Redis) и уже готовые отчёты (`GET /reports`). Аватары подгружаются пачками (`POST /parse/avatars`).
3. `POST /parse/start` создаёт запись в `parse_jobs` и задачу BullMQ. Анализы разных чатов встают в очередь (worker обрабатывает до 4 задач параллельно); один и тот же чат не может стоять в очереди дважды, а повторный анализ ограничен `CHAT_REPARSE_COOLDOWN_MINUTES`, а бесплатный лимит в сутки — `FREE_ANALYSES_PER_DAY` (по умолчанию 3).
4. Worker берёт lease на Telegram-сессию пользователя (чтобы API и worker не открыли её одновременно — иначе Telegram отвечает `AUTH_KEY_DUPLICATED`), читает историю и передаёт каждое сообщение в `ChatReportBuilder` из `packages/shared`. Текст сразу сводится к счётчикам, сам текст нигде не сохраняется.
5. Прогресс (`phase`, `scannedMessages / totalMessages`) пишется в Redis и уходит в браузер по WebSocket; при обрыве сокета клиент опрашивает `GET /parse/status`.
6. Готовый отчёт сохраняется одним JSON-документом в `chat_reports` (версия схемы `ChatReport.version`) в одной транзакции с завершением задачи. Производные метрики и «Главное» (`deriveReportMetrics`, `deriveInsights`) вычисляются при чтении, а `normalizeReport` дочищает старые отчёты (стоп-слова, новые поля), поэтому аналитику можно улучшать без перепарсинга.
7. Если пользователь нажал Start в нашем боте (`TELEGRAM_BOT_TOKEN`), worker пишет ему «Отчёт готов» с кнопкой на отчёт. Бот узнаёт человека по Telegram id отправителя `/start` — это тот же аккаунт, что вошёл на сайт; `/stop` или кнопка в аккаунте выключают. Опрашивает бота (long polling) только один worker под замком в Redis. Кнопка «Открыть» — `login_url`: Telegram открывает сайт в своём браузере (там нет cookie) на `/auth/telegram?to=…` и добавляет id нажавшего с подписью токеном бота; страница передаёт поля в `POST /api/v1/auth/telegram-login`, API проверяет подпись (HMAC-SHA256 ключом SHA-256 токена), свежесть (10 минут) и одноразовость (Redis) и открывает сеанс тому, кто уже входил на сайте. Без домена у бота в @BotFather Telegram такую кнопку не принимает — бот шлёт обычную ссылку.

## Модули API

| Модуль     | Ответственность                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| `auth`     | вход через Telegram, JWT access + ротируемые refresh-семьи, WS-tickets                                     |
| `account`  | пользователи, настройки, Telegram-сессии; «Выйти» с последнего устройства стирает сессию Telegram          |
| `parse`    | диалоги, очередь, прогресс, анализ, восстановление задач после сбоя Redis                                  |
| `reports`  | чтение и удаление отчётов                                                                                  |
| `share`    | ссылки на отчёт и угадайку (`share_links`), публичные `/api/v1/public/:token`                              |
| `notify`   | «Уведомления» (таблица `notifications`, `notify()`), свой Telegram-бот повторяет важные; `/start`, `/stop` |
| `system`   | `/health`, `/ready` (Postgres, Redis, heartbeat worker), очистка по retention                              |
| `telegram` | шлюз к Telegram: `live` (teleproto — поддерживаемый форк GramJS) и `fake` (детерминированный демо-аккаунт) |

Контракт эндпоинтов (`ApiEndpointMap`) и zod-схемы лежат в `packages/shared/src/api`, клиент вызывает их типобезопасно через `api('GET /api/v1/...')`.

## Веб-клиент

- Страницы: `/` (лендинг), `/privacy`, `/login`, `/dashboard`, `/new`, `/notifications`, `/chat/:id`, `/account`, `/example` (публичный пример отчёта, собирается в браузере тем же `ChatReportBuilder`), `/s/:token` (ссылка без входа: отчёт или угадайка), `/offline`.
- Ссылки (`share_links`): у отчёта одна ссылка каждого вида. Данные копируются в ссылку в момент создания: имя собеседника, слова, стикеры — только если владелец включил; Telegram id и id сообщений вырезаются. Угадайка хранит 5 вопросов из `deriveQuiz` и один ответ гостя; счёт виден автору только с согласия гостя. Удаление отчёта или аккаунта удаляет ссылки (каскад).
- Страницы после входа (`/dashboard`, `/new`, `/notifications`, `/account`, `/chat/**`) рендерятся только на клиенте (`ssr: false` в `routeRules`; e2e это проверяет): Vue не исправляет расхождения классов после гидратации.
- Access-token живёт только в памяти; при загрузке страницы клиент обновляет его по HttpOnly refresh-cookie. Вкладки синхронизируют обновление через Web Locks.
- Аналитика — чистые функции в `packages/shared/src/analytics` с тестами; web и API используют один код.
- Стили — CSS-переменные (`assets/styles/tokens.css`), светлая и тёмная тема, без UI-фреймворка. Тексты интерфейса — `app/i18n/{en,ru}.ts`, ключи проверяются TypeScript.
- Гостевая ссылка `/s/:token`: API отвечает 404 на выключенную, удалённую или истёкшую ссылку и 400 на адрес, который не может быть ссылкой, — гость видит «Ссылка больше не работает»; любой другой сбой (сеть, 5xx, 429) — «Не получилось открыть ссылку» с «Повторить».
- В fake-режиме API помечает каждый ответ заголовком `x-telegram-mode: fake`; тестовый вход (e2e, `shots`, `measure`) без него не выполняется. В production fake-режим запрещён конфигом, заголовка там нет.
