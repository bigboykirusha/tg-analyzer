# Релиз

Чек-лист перед каждой выкладкой в production. Как устроены сервисы — в [DEPLOY.md](DEPLOY.md), переменные — в [ENVIRONMENT.md](ENVIRONMENT.md), что делать при сбоях — в [RUNBOOK.md](RUNBOOK.md).

## До выкладки

- [ ] CI зелёный на коммите релиза: lint, format, typecheck, unit-, API- и e2e-тесты.
- [ ] `pnpm audit --prod` без high и critical. Исключения записаны в описании релиза с причиной.
- [ ] В релизе есть новые миграции? Прочитайте их и `docs/migrations/*.md`. Если миграция меняет или удаляет данные, сделайте бэкап (ниже) и подготовьте откат.
- [ ] Новые переменные окружения добавлены в платформу и в `ENVIRONMENT.md`; `.env` в образ не попадает.
- [ ] `TELEGRAM_MODE=live`, `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` заданы (API с `fake` в production не стартует).
- [ ] `SESSION_ENCRYPTION_KEY`, `JWT_SECRET` и `JWT_REFRESH_SECRET` не менялись. Смена ключа шифрования делает все сохранённые Telegram-сессии нечитаемыми: пользователям придётся войти заново.
- [ ] Тексты политики и условий (`/login#privacy`, `/terms`) соответствуют тому, что код реально хранит. Черновик условий до юридической проверки не публикуется как окончательный.

## Выкладка

1. Бэкап Postgres (обязательно, если есть миграции).
2. Миграции: pre-deploy api (`pnpm --filter @tg-analyzer/api migrate`). При ошибке preflight остановитесь и разберитесь по RUNBOOK; данные автоматически не удаляйте.
3. API, затем worker, затем web. Worker после старта сам переставит потерянные задачи (`parse_job_reconciled` в логах).
4. Задачи, которые шли во время выкладки, worker продолжит или пометит ошибкой; пользователь может запустить анализ заново.

## После выкладки (10 минут)

- [ ] `GET /ready` у API отвечает `ok` по Postgres, Redis и worker.
- [ ] На боевом домене, в окне инкогнито:
  - [ ] `/login` открывается, OG-превью ссылки показывает картинку;
  - [ ] `/example` строит пример отчёта и «Итоги»;
  - [ ] вход по коду Telegram, перезагрузка страницы не выкидывает из аккаунта;
  - [ ] анализ небольшого чата: прогресс идёт, отчёт открывается;
  - [ ] «Аккаунт и приватность»: отключение Telegram и выход работают.
- [ ] В логах API и worker нет всплеска `error` за первые 10 минут.

Если что-то из этого не работает и быстро не чинится — откат (ниже).

## Откат

- Код: передеплоить предыдущий успешный деплой в платформе. Отчёты хранятся одним JSON-документом с версией схемы, а чтение терпит старые и новые поля, поэтому откат кода без отката БД обычно безопасен.
- Миграция: только по её down-скрипту (`docs/migrations/*-down.sql`), при остановленных API и worker. Если down-скрипта нет — восстановление из бэкапа.

## Бэкапы

- Postgres — единственное хранилище, которое нужно бэкапить. В Redis лежат очереди, кэши и временное состояние входа: после потери Redis worker восстановит задачи из `parse_jobs`, остальное пересоздастся.
- Ежедневный автоматический бэкап средствами платформы (Railway: Backups у сервиса Postgres) с хранением не меньше 7 дней.
- Ручной бэкап перед миграцией:

  ```sh
  pg_dump --format=custom --no-owner "$DATABASE_URL" > tg-analyzer-$(date +%F).dump
  ```

- Восстановление в пустую базу:

  ```sh
  pg_restore --no-owner --clean --if-exists --dbname "$DATABASE_URL" tg-analyzer-YYYY-MM-DD.dump
  ```

- Раз в квартал восстановите бэкап в отдельную базу и откройте пару отчётов: бэкап, который ни разу не восстанавливали, бэкапом не считается.
- В бэкапе есть зашифрованные Telegram-сессии и отчёты пользователей. Храните его с тем же доступом, что и production-базу, и удаляйте по истечении срока: удаление аккаунта должно доходить и до бэкапов через их ротацию (`DATA_RETENTION_DAYS` касается только живой базы).
