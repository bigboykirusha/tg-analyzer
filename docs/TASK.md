# РОЛЬ

Ты — принципал-инженер (full-stack TypeScript) и продуктовый дизайнер-фронтендер в одном лице. Твоя задача — взять старый, неаккуратно написанный проект и довести его до состояния, в котором его можно безопасно выкатить в production и показать реальным пользователям.

# ПРОЕКТ

Репозиторий: https://github.com/bigboykirusha/tg-analyzer (локально — текущая рабочая директория).

TG Analyzer — дашборд для анализа Telegram-чатов.
Известный стек (по README, перепроверь по коду):
- pnpm workspace (monorepo): `apps/*`, `packages/shared`, `scripts`, `docs`
- Web: Nuxt (деплой на Vercel: tg-analyzer-web.vercel.app)
- API: Fastify
- Worker: BullMQ + Redis
- БД: PostgreSQL (миграции через `db:migrate`, `db:push`)
- Интеграция: Telegram API (api_id / api_hash с my.telegram.org)
- Node 22+, Corepack, Docker Compose
- Команды проверки: `corepack pnpm check`, `corepack pnpm build`

Код писался давно и местами плохо. Не доверяй существующим решениям — проверяй их.

# ГЛАВНАЯ ЦЕЛЬ

Production-ready продукт:
1. Работает корректно end-to-end: от входа пользователя до отображения результатов анализа.
2. Безопасен (особенно с учётом того, что продукт работает с Telegram-сессиями и перепиской людей).
3. Устойчив, наблюдаем, воспроизводимо деплоится.
4. Имеет современный, аккуратный, цельный дизайн и безупречный адаптив (mobile-first).
5. Кодовая база читаема, типобезопасна, покрыта тестами на критичную логику.

Категории аудита (проверь каждую):

**A. Корректность и бизнес-логика**
- Что именно считает «анализ чата»? Проверь формулы метрик: активность, топ участников, временные распределения, слова/эмодзи, ответы/цепочки и т.д. Найди ошибки: часовые пояса, DST, off-by-one в диапазонах дат, учёт удалённых/служебных/пересланных сообщений, дубли, пагинация истории, лимиты.
- Корректность жизненного цикла задачи анализа: создание → очередь → прогресс → результат → ошибка → повтор → отмена → очистка.
- Идемпотентность воркера, повторные запуски, дедупликация, гонки при параллельных задачах, зависшие задачи (stalled jobs), поведение при рестарте.
- Обработка лимитов Telegram (FLOOD_WAIT, SESSION_REVOKED, AUTH_KEY_*, приватные/недоступные чаты, миграция чатов), бэкофф и честные сообщения пользователю.
- Граничные случаи: пустой чат, чат на миллионы сообщений, чат без текста, один участник, удалённые аккаунты, не-латинские и RTL-символы, emoji/ZWJ-последовательности, очень длинные сообщения.
- Единая точка правды для типов и доменных констант — `packages/shared`. Найди дублирование типов между apps.

**B. Безопасность и приватность (критично: это чужая переписка и Telegram-сессии)**
- Хранение Telegram session string / токенов: шифруется ли, где ключ, ротация, возможность отзыва и полного удаления данных пользователя.
- Аутентификация и сессии: cookie flags (HttpOnly, Secure, SameSite), срок жизни, ротация, CSRF, защита от fixation, брутфорс/rate limiting на вход и на ввод кода Telegram/2FA-пароля.
- Авторизация: проверка владения ресурсами на КАЖДОМ эндпоинте (IDOR). Пользователь A не должен видеть анализы пользователя B.
- Валидация всех входов (схемы Zod/TypeBox или аналог на границе API), ограничение размеров, санитизация вывода (XSS через имена чатов/сообщения).
- CORS, security headers (helmet/CSP), trust proxy, HTTPS-only.
- Секреты: дефолтные значения в `.env.example`, валидация env при старте (приложение должно падать с понятной ошибкой, если конфиг невалиден), отсутствие секретов в логах и ответах API.
- Зависимости: `pnpm audit`, устаревшие/уязвимые пакеты.
- Что хранится из содержимого сообщений? Минимизируй: храни агрегаты, а не сырые тексты, если это не требуется продуктом. Предложи политику хранения (TTL) и реализуй удаление данных по запросу пользователя.
- Логи: без PII и текстов сообщений.

**C. Архитектура и качество кода**
- Разделение слоёв (routes → services → repositories), отсутствие бизнес-логики в хендлерах и компонентах.
- Циклические зависимости, god-файлы, копипаста, мёртвый код, неиспользуемые экспорты/зависимости (используй knip/depcheck/ts-prune или аналог).
- Строгий TypeScript: `strict`, `noUncheckedIndexedAccess`, запрет `any`, корректные границы типов между API и web (общие схемы из `packages/shared`, типобезопасный клиент).
- Единая обработка ошибок: типизированные ошибки, единый формат ответа об ошибке, коды, request-id.
- Конфигурация: единый загружаемый и валидируемый конфиг, без `process.env` по всему коду.
- ESLint + Prettier (+ Nuxt/Vue правила), единые правила на весь монорепо, pre-commit (lint-staged/husky или lefthook).
- Именование, структура папок, консистентность.

**D. База данных и очереди**
- Схема: нормализация, типы колонок, ограничения, внешние ключи, индексы под реальные запросы (проверь EXPLAIN на ключевых запросах), каскады удаления.
- Миграции: воспроизводимость с нуля, отсутствие дрифта между `db:push` и `db:migrate`; убери `db:push` из прод-пути.
- N+1, большие выборки без пагинации, транзакции там, где нужна атомарность, пул соединений.
- BullMQ: настройки attempts/backoff, removeOnComplete/Fail, concurrency, rate limiter, graceful shutdown воркера, лимиты на размер job data, мониторинг.
- Redis: политика вытеснения, персистентность, не использовать как единственное хранилище важных данных.

**E. Производительность**
- Горячие пути API и воркера, потоковая/пакетная обработка больших чатов вместо загрузки всего в память.
- Кэширование результатов, ETag/Cache-Control где уместно.
- Web: размер бандла, ленивая загрузка, SSR/CSR-стратегия по страницам, тяжёлые графики, виртуализация длинных списков, Web Vitals (LCP/CLS/INP).

**F. Надёжность и эксплуатация**
- Healthcheck/readiness эндпоинты (API, worker), graceful shutdown.
- Структурированные логи (pino), корреляция по request-id/job-id.
- Метрики и ошибки: Sentry (или аналог) + базовые метрики; алерты-кандидаты описать в docs.
- Dockerfile’ы для api/worker/web (multi-stage, non-root, малый образ, .dockerignore), `docker-compose` для прод-подобного окружения, отдельно от dev.
- CI (GitHub Actions): install с кэшем → lint → typecheck → test → build → audit; миграции в деплое; артефакты.
- Бэкапы БД и план восстановления (docs).
- Реши, где живёт каждая часть в проде (web на Vercel; API/worker/Postgres/Redis — где?), и задокументируй рекомендуемую схему деплоя, переменные окружения для каждого сервиса, домены и cookie-домен для кросс-доменной схемы (SameSite/CORS!).

**G. Тесты**
- Юнит-тесты на всю аналитическую логику (чистые функции метрик) — максимально полно, включая граничные случаи из пункта A.
- Интеграционные тесты API (с тестовым Postgres/Redis через testcontainers или compose): аутентификация, авторизация (IDOR), жизненный цикл задачи, валидация.
- Тест воркера с мокнутым Telegram-клиентом (FLOOD_WAIT, падение посреди задачи, повторный запуск).
- Минимальные E2E (Playwright) на ключевой пользовательский путь на desktop и mobile viewport.
- Порог покрытия для критичных модулей, тесты запускаются в CI.

**H. Дизайн, UX и адаптив (отдельный приоритетный блок — см. Фазу 3)**

## Цель

Интерфейс уровня топовых iOS-приложений 2026 года: человек открывает сайт на iPhone и ощущает нативное приложение, а не панель разработчика. Критерии: современно, цельно, плавно, читаемо, безупречно на любом экране.

## Дизайн-направление: iOS 26 / Liquid Glass, но читаемо

1. Стекло (полупрозрачность + размытие) только для навигации и слоёв: плавающий нижний таб-бар, верхняя шапка, bottom sheet, модалки, тосты, меню. Карточки с данными и графики остаются плотными непрозрачными поверхностями, чтобы цифры читались идеально.
2. Глубина через слои, а не через рамки: мягкие многослойные тени, тонкий внутренний световой кант, без жёстких бордеров.
3. Крупная уверенная типографика (large title как в iOS), крупные метрики, `font-variant-numeric: tabular-nums`.
4. Щедрые отступы, скругления 16–28px, капсулы для кнопок и чипов, концентричные радиусы.
5. Живой, но сдержанный motion: пружины, отклик на касание, плавные переходы.
6. Один брендовый акцент + нейтральная палитра. Цвет несёт смысл (рост/падение/статус), а не украшение.

Стекло обязано иметь: fallback через `@supports not (backdrop-filter: ...)`, поддержку `prefers-reduced-transparency` и `prefers-contrast: more`, ограничение числа одновременных blur-слоёв (производительность на слабых телефонах), запрет blur внутри прокручиваемых списков.

## Палитра (решает владелец продукта)

Текущий акцент: лаймовый (#e0ff5c-подобный) на графитово-чёрном. На шаге 1 подготовь ДВА варианта палитры (светлая и тёмная темы, проверенные контрасты):
- Вариант A: сохранить лайм как бренд, использовать экономно (главное действие, ключевая метрика, активный пункт) + второй акцент для второй серии данных.
- Вариант B: более «айфоновская» сдержанная палитра (холодный синий/индиго/фиолетовый акцент).
После публикации `docs/design/DESIGN.md` ОСТАНОВИСЬ и дождись выбора владельца. Не продолжай до ответа.

## Токены (единый источник правды, CSS custom properties)

- Цвета семантические: `--bg`, `--bg-elevated`, `--surface`, `--surface-glass`, `--text`, `--text-secondary`, `--text-tertiary`, `--accent`, `--accent-2`, `--positive`, `--negative`, `--warning`, `--separator`. Светлая и тёмная темы + «системная» (`prefers-color-scheme`) + ручной переключатель с сохранением; `color-scheme` и `theme-color` для обеих тем.
- Контраст: текст ≥ 4.5:1, крупный ≥ 3:1, в обеих темах. Запрещены серые подписи вроде #555 на тёмном фоне. Проверка автоматическая.
- Тёмная тема: не чисто чёрная; глубокий графитовый фон, на заднем плане очень приглушённые mesh-градиентные свечения.
- Типографика: системный стек `-apple-system, BlinkMacSystemFont, "SF Pro Display", "SF Pro Text", system-ui` + self-hosted Inter Variable (subset cyrillic + latin, `font-display: swap`, preload, `size-adjust` для фолбэка). Шкала: large title / title / headline / body / callout / footnote / caption, fluid через `clamp()`. Моноширинный шрифт убрать из интерфейса (только для технических идентификаторов, если нужны).
- Сетка отступов 4/8px; токены радиусов, теней, blur-уровней (`--blur-sm/md/lg`), z-index.
- Motion: длительности 120/200/320/480ms; кривые `--ease-standard`, `--ease-out-expo`, `--ease-spring` (через `linear()` easing).

## Анимации и микровзаимодействия

Анимируй только `transform` и `opacity`. Цель 60fps.
- Нажатия: лёгкое «проседание» (scale ~0.97) с пружинным возвратом.
- Переходы между страницами: View Transitions API (Nuxt `viewTransition`), fallback без анимации.
- Появление контента: каскад (stagger 30–50ms), skeleton-экраны со shimmer вместо спиннеров.
- Числа: count-up для ключевых метрик при первом показе.
- Графики: плавная отрисовка при появлении и плавное обновление данных; подсветка и тултип по касанию/наведению.
- Bottom sheet / модалки: выезд снизу с пружиной, свайп вниз для закрытия, фокус-ловушка, закрытие по Esc.
- Прогресс анализа: плавно интерполируемый индикатор (кольцо или полоса), статусы текстом, `aria-live`.
- Тосты: капсула сверху (в духе Dynamic Island), автоскрытие, смахивание.
- Таб-бар: активный индикатор плавно «переезжает» между пунктами.
- Смена темы: плавный кросс-фейд.
- Всё отключается или упрощается при `prefers-reduced-motion: reduce`.

## Адаптив (mobile-first, без компромиссов)

- Проверка: 320, 360, 390, 430, 768, 834, 1024, 1280, 1536, 1920; портрет и ландшафт; iPhone с Dynamic Island и Android с жестовой навигацией.
- Никакого горизонтального скролла страницы и обрезанного контента ни на одной ширине.
- Мобильная навигация: плавающий стеклянный таб-бар (капсула с отступами), учёт `env(safe-area-inset-*)`. Планшет: сворачиваемый сайдбар. Десктоп: сайдбар + широкая сетка (2–4 колонки) с ограничением максимальной ширины контента.
- `100dvh`/`svh` вместо `100vh`. Клавиатура не перекрывает поля и главную кнопку.
- Таблицы и списки на мобильном: карточки или горизонтальный скролл внутри контейнера со scroll-snap и индикатором. Длинные списки — виртуализация.
- Тап-зоны ≥ 44×44px, никаких hover-only взаимодействий.
- Убрать `user-scalable=no` и `maximum-scale=1`: масштабирование разрешено. Шрифт полей ≥ 16px (чтобы iOS не зумил при фокусе).
- Контейнерные запросы (`@container`) для компонентов в разных контекстах; `overscroll-behavior`, `touch-action`, `scroll-padding`.

Типографика и цвет:
- Убрать моно из интерфейса; цифры основным шрифтом с tabular-nums.

Графики:
- «Ход переписки по дням»: агрегация по неделям/месяцам на длинном периоде (переключатель День/Неделя/Месяц), сглаживание, область с градиентом вместо «иголок»; детализация по касанию/наведению; подписи осей не обрезаются (сейчас обрезана последняя).

- Тепловая карта активности: на всю ширину контейнера, адаптивные ячейки, подписи месяцев и дней недели, легенда интенсивности, на мобильном горизонтальный скролл со snap.

Тексты:
